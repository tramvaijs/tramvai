# Баннер об устаревшем браузере: дизайн

Дата: 2026-09-09
Статус: согласован, готов к реализации

## Задача

Показать пользователю старого браузера баннер в верхней части экрана с текстом о том, что браузер
устарел, ссылкой на инструкцию по обновлению и кнопкой скрытия.

Требования, заданные заказчиком:

1. Работает и при SSR, и при CSR.
2. По возможности работает без JavaScript. Мы не знаем, исполняется ли наш бандл в старом браузере,
   поэтому нельзя закладываться на то, что React отрендерится.
3. Нулевой CLS. Баннер не должен появляться после первой отрисовки и сдвигать контент.
4. Максимизировать вероятность того, что баннер увидит тот, кому он адресован.
5. Приложение может иметь собственную вёрстку с `position: fixed`, которой фреймворк не управляет.
   Нужны точки кастомизации стилей.

## Ключевое решение

Баннер это статический HTML, который сервер кладёт в слот `body:start`, до контейнера React, вместе
с инлайновым `<style>` в `head`. React его не рендерит и не гидрирует. Поэтому баннер виден даже
тогда, когда бандл приложения не распарсился в старом браузере, ровно в том сценарии, ради которого
он существует.

Скрытие работает на CSS через скрытый чекбокс и `label`, без JavaScript. Крошечный инлайновый
ES3-скрипт дополнительно ставит cookie, чтобы сервер не рисовал баннер на следующих страницах.
Если скрипт не отработал, баннер вернётся на следующей навигации. Это приемлемая деградация и она
согласуется с требованием 4.

CLS равен нулю, потому что баннер приходит уже отрисованным в первом HTML и находится в обычном
потоке документа. Ничего не появляется и не исчезает после первой отрисовки.

## Детект: три исхода, три поведения

`isBrowserSatisfiesRequirements` из `@tinkoff/user-agent` возвращает `true`, `false` или `null`.
Вызывается с `forceMinimumUnknownVersions: true`, этот режим в исходниках библиотеки прямо описан
как предназначенный для детекта старых браузеров.

| Исход | Смысл | Что уходит в ответ |
|---|---|---|
| `false` | браузер точно старый | видимый баннер, инлайновый CSS, скрипт установки cookie, скрипт флага |
| `true` | браузер точно свежий | ничего |
| `null` | UA не распознан | скрытый баннер, инлайновый CSS, скрипт фича-детекта, скрипт установки cookie |

Для основной массы трафика в ответ не добавляется ни байта. Реальный пробел это нераспознанный UA,
и он закрывается вторым слоем без платы за него у всех.

Второй слой это синхронный инлайновый скрипт в `head`. Он выполняет фича-детект и, если браузер не
проходит, добавляет класс на `<html>`. CSS показывает баннер по этому классу. Скрипт синхронный и
стоит в `head`, то есть отрабатывает до первой отрисовки. CLS остаётся нулевым.

Опция `featureDetect` со значениями `unknown-only` по умолчанию, `always` и `off`. Значение `always`
включает фича-детект и для распознанных свежих браузеров. Это закрывает редкий случай подменённого
UA и случай, когда бандл ломается в браузере, формально проходящем по browserslist. Цена примерно
300 байт после gzip в критическом пути у ста процентов пользователей.

Источник browserslist по умолчанию это конфиг самого приложения. Библиотека сама подхватывает его
через `@tramvai/cli/lib/external/browserslist-normalized-file-config`, если конфиг не передан явно.

## Позиционирование и конфликт с чужим `position: fixed`

Баннер остаётся в обычном потоке в начале `body` и получает `position: relative` с высоким
`z-index`. Это решает конфликт без JavaScript и без компенсации отступов.

- В потоке он занимает собственное место, поэтому не нужен `padding-top` у `body` и не нужна
  математика с высотой, которая ломается при переносе текста на узких экранах.
- За счёт `z-index` он отрисовывается поверх чужой фиксированной шапки, а не под ней.

Для типового приложения с фиксированной шапкой не требуется никаких действий.

Точки кастомизации, от самой дешёвой к самой мощной:

1. `OUTDATED_BROWSER_CLASSNAME_TOKEN` добавляет класс к корню баннера. Подходит, когда у приложения
   уже есть своя дизайн-система.
2. `OUTDATED_BROWSER_EXTRA_CSS_TOKEN` дописывает произвольный CSS в тот же инлайновый `<style>`.
   Это главный инструмент для конфликтов вёрстки. CSS приложения оказывается в критическом пути и
   применяется ровно тогда, когда баннер показан, в той же отрисовке, без JS и без CSS-переменных,
   которых нет в старых браузерах.
3. `OUTDATED_BROWSER_RENDER_TOKEN` полностью заменяет разметку баннера. Крайний случай. В документации
   явно указано, что при замене разметки нужно сохранить чекбокс с известным `id`, иначе перестанет
   работать скрытие без JS.

Инлайновые стили через атрибут `style` сознательно не поддерживаются: скрытие без JS требует правил
`:checked ~`, которые в атрибуте выразить нельзя, а частичная поддержка вводила бы в заблуждение.

## Совместимость CSS

CSS написан под самые старые браузеры, которые вообще могут дойти до баннера. Никакого flexbox,
grid, CSS-переменных, `gap` и логических свойств. Кнопка закрытия позиционируется через `float: right`
и стоит первой в исходном порядке, чтобы не сваливаться на вторую строку. Скрытие держится на
`:checked` и соседнем комбинаторе, это CSS3 уровня IE9.

Специфичность проверена. Правило скрытия `.checkbox:checked ~ .banner` имеет специфичность 0-3-0 и
выигрывает у правила показа `.detected .banner` со специфичностью 0-2-0. То есть кнопка закрытия
работает и в режиме фича-детекта.

## Инлайновые скрипты

Скрипты собираются конкатенацией строк, а не через `Function.prototype.toString` от TypeScript-функции.
Это принципиально. Транспайлер настроен на цели сборки приложения и может оставить стрелочные функции
или другой современный синтаксис, который не распарсится ровно в том браузере, ради которого всё
затевается. Строковые литералы гарантируют ES3 на выходе. Тот же приём уже используется в
`POLYFILL_CONDITION`, где значение по умолчанию это строка `'false'`.

Скрипты получают CSP-nonce от фреймворка, потому что регистрируются через `RENDER_SLOTS` с типом
`inlineScript`. Инлайновые обработчики в атрибутах не используются.

Слоты:

| Ресурс | Слот | Тип |
|---|---|---|
| CSS баннера | `head:core-styles` | `inlineStyle` |
| Фича-детект и флаг | `head:performance` | `inlineScript` |
| Разметка баннера | `body:start` | `asIs` |
| Установка cookie при скрытии | `body:end` | `inlineScript` |

Скрипт установки cookie стоит в `body:end`, потому что ему нужен уже существующий в DOM чекбокс.
Персистентность скрытия не критична по времени, поэтому конец body подходит.

## Флаг для React

`IS_OUTDATED_BROWSER_TOKEN` даёт булев флаг через DI, хук `useIsOutdatedBrowser` даёт его в
компонентах. На сервере это вычисленное значение. В браузере это `window.__TRAMVAI_OUTDATED_BROWSER__`,
который выставляют инлайновые скрипты. Отдельная синхронизация состояния не нужна, глобальный флаг
переживает SPA-навигации, и это тот же приём, что уже используется в `@tramvai/module-client-hints`
для `window.__TRAMVAI_USER_AGENT_DATA`.

Флаг отражает «браузер устарел», а не «баннер показан». Поэтому скрипт фича-детекта отправляется
даже пользователю, который уже скрыл баннер cookie. Разметка и CSS в этом случае не отправляются.

## Кэширование

Ответ зависит от `User-Agent` и от cookie скрытия. Без учёта этого закэшированный ответ с баннером
уйдёт всем подряд.

Заголовок `Vary` дополняется значениями `User-Agent` и `Cookie` через `RESPONSE_MANAGER_TOKEN` на
стадии `commandLineListTokens.customerStart`. Существующее значение заголовка читается и дополняется,
а не перезаписывается. Опция `vary: false` отключает это для приложений за CDN, который уже
нормализует UA. По умолчанию опция включена, потому что молча отдавать неверный баннер хуже, чем
потерять часть попаданий в кэш. Стоимость `Vary: User-Agent` для CDN описана в документации модуля.

Для кэша статических страниц в `@tramvai/module-page-render-mode` нужен вклад в ключ кэша.
Существующий `STATIC_PAGES_KEY_TOKEN` объявлен одиночным провайдером с дефолтом `''`, приложения
переопределяют его целиком, поэтому модуль баннера не может его предоставить, не отобрав ключ у
приложения.

Решение: в `@tramvai/tokens-render` добавляется multi-токен `RENDER_CACHE_KEY_PART_TOKEN` типа
`() => string` с request-скоупом. Дефолтная фабрика `STATIC_PAGES_KEY_TOKEN` склеивает все части.
Модуль баннера предоставляет свою часть. Токен живёт в пакете токенов, потому что его предоставляет
один модуль, а потребляет другой, и прямая зависимость между ними не нужна.

Обратная совместимость сохраняется: приложения, которые переопределяют `STATIC_PAGES_KEY_TOKEN`
целиком, работают как раньше, но теряют части. Это описано в документации.

## Состав пакета

Новый пакет `packages/modules/outdated-browser`, имя `@tramvai/module-outdated-browser`.

```
src/
  tokens.ts              публичные токены и типы
  private-tokens.ts      внутренний токен вычисленного состояния запроса
  constants.ts           имена классов, id чекбокса, дефолты
  shared/detect.ts       detectBrowserSupport, чистая функция
  server/sanitize.ts     sanitizeHref, sanitizeCookieName
  server/banner.ts       renderBannerHtml
  server/styles.ts       buildBannerCss
  server/inlineScripts.ts    сборка ES3-строк
  server/state.ts        вычисление состояния запроса
  server/providers.ts    провайдеры RENDER_SLOTS, Vary, ключ кэша
  browser/providers.ts   флаг из глобальной переменной
  react/useIsOutdatedBrowser.ts
  server.ts              точка входа сервера, main
  browser.ts             точка входа браузера
```

Каждый файл имеет одну зону ответственности и тестируется отдельно. Сборка разметки, стилей и
скриптов это чистые функции от аргументов, поэтому покрываются обычными unit-тестами без DI.

## Безопасность

Весь текст из токена контента экранируется через `encodeForHTMLContext` из `@tramvai/safe-strings`.

Ссылка дополнительно проверяется по схеме. Разрешены `http:`, `https:`, протокол-относительные и
относительные пути. Всё остальное, включая `javascript:`, отбрасывается, и ссылка не рендерится.
Экранирования одного недостаточно, потому что `javascript:alert(1)` не содержит символов, которые
экранирует `encodeForHTMLContext`.

Имя cookie попадает внутрь строкового литерала JavaScript, поэтому проверяется по набору символов
токена cookie из RFC 6265. Невалидное имя отбрасывается в пользу дефолтного, с записью в лог.

## Что сознательно не делается

- Определение поддержки синтаксиса ES6. Требует `eval` или `new Function`, что ломается при строгом
  CSP. Фича-детект по наличию объектов достаточен и честен. В документации описано, как приложение
  может задать свой предикат.
- Интернационализация внутри модуля. Контент приходит из токена, который резолвится через DI, поэтому
  приложение подключает свой i18n самостоятельно. Модуль не тянет зависимость на `@tramvai/module-i18n`.
- Анимация появления и скрытия. Любая анимация это риск для CLS и лишний вес в критическом пути.
