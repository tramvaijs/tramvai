# ADR: стриминг deferred-запросов react-query

2026-10-12 · Mikhail Remmele

**Статус:** предложено, на согласовании с командой.

## Контекст

При streaming-рендере долгие данные уже можно отдавать после шелла через deferred actions, но запросы react-query этого не умеют. `prefetchAction` всегда блокирует шелл, поэтому один медленный эндпоинт задерживает всю страницу.

`useSuspenseQuery` без prefetch делает запрос на сервере, но его результат не попадает на клиент. Из-за этого клиент запрашивает данные повторно или гидрация расходится с серверным HTML.

Цель: долгий запрос не блокирует шелл, его результат приходит в том же HTTP-ответе прямо в кэш react-query, а повторного запроса из браузера нет.

## Решение

На сервере мы не ждём deferred-запрос, а стримим его результат отдельным `<script>` после шелла. На клиенте запрос гидрируется с промисом этого результата. Используем штатную гидрацию pending-запросов из react-query v5.

1. **Включение.** Opt-in через `QUERY_STREAMING_ENABLED_TOKEN`, по умолчанию выключено, требуется `@tanstack/react-query@>=5.100.2`. Child app включает его у себя отдельно. Реально стриминг работает только при streaming-рендере, это отражает вычисляемый `QUERY_STREAMING_ACTIVE_TOKEN`. В остальных случаях deferred-запрос ожидается как обычный.
2. **API.** Опция `deferred: true` в `createQuery` и `createInfiniteQuery`, переопределение для страницы через `prefetchAction(options, { deferred })`. Новые хуки `useSuspenseQuery` и `useSuspenseInfiniteQuery`.
3. **Сервер.** Deferred-prefetch запускается и не ожидается. При дегидрации запрос «в полёте» уходит как pending с маркером вместо промиса, а результат стримится по ключу `react-query:{propKey}:{queryHash}`. Запросы, начатые после дегидрации (suspense-компоненты, вложенные запросы), ловим подпиской на QueryCache и шлём так же. Ретраи на сервере отключены, если не заданы явно.
4. **Клиент.** Запрос гидрируется сразу, с промисом из реестра стрима. При ошибке или таймауте он откатывается в pending и выполняется на клиенте с опциями компонента. Если клиент уже сам грузит этот запрос, застримленный результат игнорируется.
5. **Транспорт.** В render-модуле общий транспорт, не завязанный на react-query: `stream(key, promise)`, `emit(channel, payload)` и `onFinish(cb)`. Он даёт три гарантии:
    - скрипты пишутся только после шелла, иначе на React 18 ломается гидрация;
    - ответ держится открытым, пока все значения не завершатся. Для этого `closeQueue` дожидается и задач, добавленных уже во время ожидания;
    - по таймауту рендера все незавершённые значения реджектятся до закрытия стрима, как сейчас deferred actions. Поэтому клиент всегда получает resolve или reject.

## Альтернативы

| Вариант | Почему не выбран |
| --- | --- |
| Обернуть запрос в deferred action + `<Await>` | Данные оказываются вне кэша react-query, их приходится дублировать и вручную класть в кэш. Поздние и suspense-запросы так не покрыть. |
| Расширить `__TRAMVAI_DEFERRED_ACTIONS` | Ключи там регистрируются заранее в `<head>`, а поздние запросы заранее неизвестны. Нет каналов событий. |
| `ReactQueryStreamedHydration` из `@tanstack/react-query-next-experimental` | Завязан на `useServerInsertedHTML` из Next.js, в tramvai аналога нет. |
| Долгие запросы уводить на клиент (`onlyBrowser`) | Лишний round-trip из браузера, контент не виден до загрузки JS. |

## Последствия

- Медленный запрос не блокирует шелл, данные приходят без повторного запроса из браузера. Для продуктового кода это один флаг.
- `closeQueue` теперь ждёт задачи, добавленные во время закрытия. Это касается всех фич, которые пишут в стрим, включая deferred actions.
- Ответ держится открытым дольше, а QueryClient живёт до конца стрима. Верхняя граница — `REACT_STREAMING_RENDER_TIMEOUT`.
- Транспорт создаётся только при streaming-рендере через `ReactRenderServer`. С `CUSTOM_RENDER` и без concurrent features стриминг react-query не работает.
- В продакшене детали серверной ошибки на клиент не уходят, падение видно только в серверных логах (уровень debug).

## Известные ограничения

- **Цепочки запросов.** Запрос, начатый уже после того, как стрим закрылся (например, `prefetchQuery` после `await` другого запроса в самом конце ответа), не стримится, и клиент выполняет его сам. Зависания нет, но данные идут отдельным запросом.
- **Водопады вложенных Suspense.** Вложенный suspense-запрос стартует только после рендера родительского блока. Если цепочка не укладывается в таймаут, хвост рендерится на клиенте.
- **Совместимость с react-query v4.** `@tramvai/react-query` статически импортирует `useSuspenseQuery` и `useSuspenseInfiniteQuery`, которых в v4 нет. Сборка на v4 даст предупреждение webpack, а падение будет только при вызове хука.

## На подумать до переноса

- [ ] Проверить версии React и react-query в приложениях. Решить, нужна ли поддержка v4 для хуков (динамический доступ, как к `Hydrate`) или поднимаем минимальную версию.
- [ ] Не пишут ли бизнес-модули в response stream сами (скрипты до шелла ломают React 18) и не переопределяют ли `closeQueue` или дегидрацию.
- [ ] Нужна ли клиентская подстраховка на обрыв соединения: реестр реджектит висящие значения на `DOMContentLoaded`. У deferred actions такой подстраховки тоже нет.
- [ ] Метрики: число застримленных запросов, откатов на клиент, таймаутов. Сейчас есть только debug-лог.
- [ ] Перевод deferred actions и streamed store events на общий транспорт. У `StoreSyncEventsMiddleware` та же проблема со скриптами до шелла.
- [ ] Делаем ли `STREAMING_TRANSPORT_TOKEN` публичным API или держим внутренним.
- [ ] Включать ли стриминг в child app автоматически, если он включён у хоста. Сейчас токен в child app нужно задавать отдельно.
